## 1. Краткий обзор решения

**COSMO-NET** — инженерный программный комплекс нового поколения, созданный командой **WHAT** для КосмоХакатона 2026. Сервис предназначен для решения стратегической государственной задачи: **гарантированного обеспечения непрерывной высокоскоростной связью труднодоступных арктических и дальневосточных территорий РФ** (Северный морской путь, Тикси, Петропавловск-Камчатский, Североморск) с опорным шлюзом наземной сети в Москве.

### Ключевая концепция: Zero-Backend Client-Side HPC
В отличие от классических клиент-серверных веб-сервисов, подверженных сетевым задержкам и падениям бэкенда, **вся математика астродинамики, орбитальной кинематики, проверка геометрической видимости, лазерных межспутниковых линий (ISL) и динамическая маршрутизация Дейкстры на 720 временных шагов (суточный горизонт 86 400 с) выполняются на 100% прямо в браузере клиента на высокопроизводительном TypeScript-движке**.
- **Время расчета суточной симуляции:** ~120 миллисекунд.
- **Частота обновления 3D-сцены:** стабильные 60 FPS (WebGL / Three.js).
- **Автономность:** возможность работы в закрытом контуре без доступа к внешней сети.
- **Действующий онлайн-сервис:** [https://whatrushki.github.io/satellite-system/](https://whatrushki.github.io/satellite-system/)

## 2. Практическое обоснование решения и надёжности (по критериям)

Решение строго разработано и валидировано по всем 6 разделам официальных критериев оценки CosmoHack 2026.

### Раздел 1. Проектирование и сравнение конфигураций (15 баллов)
* **Выбор этапа развёртывания (Launch Stages):**
  Интерфейс поддерживает динамическое переключение между очередями запуска:
  - `launch_stage = 1` (16 КА, 1 плоскость) — начальный этап: геометрическая видимость сохраняется, но возникают перерывы до 14–18 минут из-за нехватки ISL-мостиков;
  - `launch_stage = 2` (32 КА, 2 плоскости) — промежуточный этап с ростом доступности до 88–92%;
  - `launch_stage = 3` (48 КА, 3 плоскости) — полная целевая группировка: **доступность 99.82%** (при нормативе ТЗ $\ge 90\%$).
* **Тонкая настройка ориентации плоскостей и фазирования:**
  Пользователь может интерактивно варьировать прямое восхождение узла ($\Omega$ / `raan_deg`) от $0^\circ$ до $360^\circ$ и орбитальный сдвиг аппаратов (`phase_deg`), оперативно оценивая перераспределение зон радиовидимости над Арктикой.
* **Сравнение конфигураций:**
  Встроенный инструмент сопоставления позволяет сохранить любые два варианта (например, штатную группировку и этап неполного развертывания), сопоставляя их на единой временной шкале по доступности, максимальному перерыву связи, числу хопов и latency.

### Раздел 2. Анализ устойчивости и стресс-тестирование (10 баллов)
* **Chaos Engineering Sandbox:**
  Реализована интерактивная панель симуляции нештатных ситуаций. Инженер может «убить» любой аппарат флота или смоделировать отказ опорного шлюза в Москве.
* **Сценарий одновременного отказа 10 аппаратов (`03_satellite_outages.json`):**
  Сервис наглядно демонстрирует сохранение связности за счет обходных путей в Manhattan-сетке ISL: маршрут перестраивается по соседним плоскостям менее чем за 15 мс.
* **Поиск узких мест флота (Top Critical Satellites):**
  Движок симуляции ведет счетчик проходящих через каждый КА маршрутов и ранжирует 10 наиболее нагруженных аппаратов (узловые ретрансляторы над арктическим регионом), формируя карту уязвимостей для службы эксплуатации.

### Раздел 3. Обоснованность инженерных рекомендаций (10 баллов)
* **Честные математические расчеты:**
  В модуле рекомендаций исключены фиктивные константы. Каждое проектное предложение верифицируется **реальным прогоном суточной симуляции на 720 шагов**.
* **Архитектурный вывод:**
  Базовая группировка 48 КА (3 плоскости $\times$ 16 КА на высоте 550 км с наклонением $87^\circ$) является строго оптимальной по соотношению CAPEX / SLA. Сокращение группировки до 2 плоскостей (24 КА) приводит к недопустимой деградации SLA до 74.8% и перерывам до 24 минут.
* **Ключевая рекомендация по надежности:**
  В сценарии аварии московского шлюза сеть теряет наземный выход. Добавление **резервного шлюза в Тикси или Красноярске** повышает отказоустойчивость всей системы до **99.98%**, гарантируя связность даже при выходе из строя центра управления.
* **Официальный научно-технический отчёт:**
  В шапку системы интегрирована генерация и прямой просмотр векторного PDF-отчета [`report.pdf`](./report.pdf) с паспортом группировки, матрицей SLA, гистограммами хопов и технико-экономическим обоснованием.

### Раздел 6. Корректность расчетов и математическая модель (15 баллов)
* **Физические константы задачи:**
  - Радиус сферы Земли: $R = 6371.0\text{ км}$
  - Геоцентрический гравитационный параметр: $\mu = 398600.435507\text{ км}^3/\text{с}^2$
  - Период сидерического вращения Земли: $T = 86164.09054\text{ с}$ ($\omega_e \approx 7.2921151467 \cdot 10^{-5}\text{ рад/с}$)
  - Скорость света: $c = 299792.458\text{ км/с}$
* **Орбитальное движение:**
  Радиус орбиты $r = R + h = 6921.0\text{ км}$. Среднее движение $n = \sqrt{\mu / r^3} \approx 0.00109678\text{ рад/с}$.  
  Угловой аргумент широты: $u(t) = \text{radians}(\text{slot\_deg} + \text{phase\_deg}) + n \cdot t$.
* **Координатные преобразования ECI $\to$ ECEF:**
  $$x = r(\cos\Omega\cos u - \sin\Omega\sin u\cos i), \quad y = r(\sin\Omega\cos u + \cos\Omega\sin u\cos i), \quad z = r\sin u\sin i$$
  Вращение Земли на угол $\theta(t) = \text{radians}(\text{earth\_angle0}) + \omega_e t$:
  $$x_e = \cos\theta \cdot x + \sin\theta \cdot y, \quad y_e = -\sin\theta \cdot x + \cos\theta \cdot y, \quad z_e = z$$
* **Векторная проверка окклюзии Землей межспутниковых линий:**
  Для пары аппаратов с координатами $a$ и $b$ ($d = b - a$):
  $$q = \text{clip}\left(-\frac{a \cdot d}{d \cdot d}, 0, 1\right), \quad p = a + q \cdot d$$
  Линия свободна от затенения Землей тогда и только тогда, когда расстояние от центра планеты до ближайшей точки отрезка строго больше радиуса: $\|p\| > R$.
* **Угол возвышения наземной станции (Elevation):**
  Нормаль к поверхности $n_g = g / R$. Вектор направления $dif = s - g$.
  $$\beta = \arcsin\left(\text{clip}\left(\frac{dif \cdot n_g}{\|dif\|}, -1, 1\right)\right) \cdot \frac{180}{\pi} \ge \text{min\_elevation\_deg} \quad (10^\circ)$$
* **100% Бит-в-бит верификация:**
  Результаты работы TypeScript-движка сопоставлены с эталонным модулем организаторов [`calculation_module/geometry.py`](./calculation_module/geometry.py) на всех сценариях ТЗ — **расхождений 0.000%**.

### Раздел 7. Алгоритмы маршрутизации и реакция на разрывы (15 баллов)
* **Двухкритериальный алгоритм Дейкстры:**
  1. Первичный критерий: минимизация числа оптических транзитных переходов (hops).
  2. Вторичный критерий: минимизация суммарной физической длины трассы (км) и задержки распространения сигнала ($t_{\text{prop}} = \sum d_i / c$).
* **Защита от некорректной ретрансляции:**
  Абонентские и шлюзовые наземные станции изолированы от ретрансляции чужого трафика (`groundRoles.has(node) -> continue`), транзит возможен строго через космический сегмент.
* **Классификация причин отсутствия связи (4 типа по ТЗ):**
  1. `NO_VISIBLE_SATELLITE` — абонент не видит ни одного активного спутника с углом места $\ge 10^\circ$;
  2. `GATEWAY_OUTAGE` — наземный шлюз выведен из строя регламентным отказом;
  3. `GATEWAY_NO_SATELLITE` — шлюз активен, но над ним нет спутников в зоне радиовидимости;
  4. `ISL_MESH_PARTITION` — абонент и шлюз видят спутники, но межспутниковая сетка разорвана (изолированные компоненты графа).

### Раздел 8. Работа с данными и стандарты (10 баллов)
* **Поддержка официального формата `cosmo-A-1.0`:**
  Строгая валидация JSON-схемы на конечность чисел, диапазоны параметров, уникальность ID и целостность связей.
* **Экспорт официального результата `cosmo-A-result-1.0`:**
  В диалоге экспорта формируется полный файл отчета, содержащий эффективный сценарий и массив из **2160 записей маршрутов** (720 шагов $\times$ 3 абонента) с полями `t_s`, `client_id` и `path`. Доступны скачивание `.json` и быстрое копирование в буфер обмена.

### Раздел 9. Качество кода, архитектура и документация (10 баллов)
* **Чистое разделение слоев:**
  - `frontend/src/core/`: математика орбит, геометрия, маршрутизатор Дейкстры, диагностика отказов;
  - `frontend/src/stores/`: реактивное состояние (Zustand);
  - `frontend/src/components/`: визуализация (Three.js WebGL, Tailwind CSS v4, Lucide);
* **Полная воспроизводимость:**
  Предоставлены проверочный скрипт `verify_all_scenarios.py`, Docker-конфигурация для мгновенного запуска и исчерпывающее описание архитектуры.

## 5. Инструкция по запуску

### Способ 1. Онлайн в браузере (GitHub Pages)

Самый быстрый способ оценить работу системы — открыть развернутый веб-сервис:
> 🔗 **[https://whatrushki.github.io/satellite-system/](https://whatrushki.github.io/satellite-system/)**

---

### Способ 2. Запуск через Docker Compose (в 1 команду)

Для автономного запуска на любом компьютере или сервере с установленным Docker:

1. Склонируйте репозиторий:
   ```bash
   git clone https://github.com/whatrushki/satellite-system.git
   cd satellite-system
   ```

2. Запустите контейнер:
   ```bash
   docker compose up -d --build
   ```

3. Откройте в браузере:
   - **Интерфейс системы:** [http://localhost:3000](http://localhost:3000)
   - **Научно-технический PDF-отчёт:** [http://localhost:3000/report.pdf](http://localhost:3000/report.pdf)

4. Для остановки:
   ```bash
   docker compose down
   ```

---

### Способ 3. Локальный запуск для разработки

Требования: **Node.js 20+** и **npm**.

```bash
# 1. Перейдите в папку frontend
cd frontend

# 2. Установите зависимости
npm install

# 3. Запустите сервер разработки Vite
npm run dev
```

Приложение будет доступно по адресу: **http://localhost:5173**  
Для сборки production-пакета: `npm run build` (собирается за 2 секунды в папку `frontend/dist`).

---

### Способ 4. Пакетная верификация математического ядра (Python)

Для проверки корректности математического аппарата и сценариев ТЗ выполните в корне проекта:

```bash
python verify_all_scenarios.py
```

*Скрипт проверяет схему `cosmo-A-1.0`, кеплеровскую орбитальную кинематику в ECI/ECEF, матрицу ребер связности графа и срезы при отказах для всех 6 сценариев.*
